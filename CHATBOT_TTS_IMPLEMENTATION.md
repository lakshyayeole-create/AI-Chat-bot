# Anantya 2026 — Chatbot & TTS Implementation Plan

**Purpose:** Implementation checklist for the Chatbot + Text-to-Speech workstream only.  
**Important:** Inspect the files available in the current workspace before choosing framework-specific paths or changing code. The full Anantya website repository may not be available.

## 1. Feature requirements

### Mode A: Chatbot Voice
- [x] Reuse the existing chatbot's final text answer.
- [x] Add a user-controlled voice toggle (voice off by default unless the existing UX specifies otherwise).
- [x] When voice is enabled, speak each final answer once.
- [x] Provide Stop and, where supported, Pause/Resume.
- [x] Cancel previous speech when a new answer starts.
- [x] Do not break normal text answers when TTS fails.

### Mode B: Read Page
- [x] Expose a `readPage(textOrContent)` entry point.
- [x] Integrate through an explicit page-content adapter or configurable selector.
- [x] Exclude navigation, buttons, hidden content, duplicate text and decorative UI.
- [x] Split long content into logical sections/chunks.
- [x] Play chunks sequentially.
- [x] Provide Stop and, where supported, Pause/Resume.
- [x] Use browser speech for any chunk that cannot be generated by ElevenLabs.
- [x] Show a helpful message if no readable content is available.

## 3. Client-side interface

Provide a small framework-independent API similar to:

```javascript
const tts = createTTSManager({
  client: ttsClient,
  browserSpeech: browserSpeechProvider
});

// Speak the final answer from the existing chatbot.
await tts.speakAnswer(answerText, { voiceEnabled: true });

// Read content explicitly supplied by the host page.
await tts.readPage(pageText);

// Playback controls.
tts.pause();
tts.resume();
tts.stop();

// Optional state subscription for UI controls.
const unsubscribe = tts.subscribe((state) => {
  // state: idle | loading | playing | paused | fallback | error
});
```

This is an interface proposal, not a requirement to use these exact names. Keep provider details out of the chatbot component. Handle overlapping requests, cancellation, browser support checks and cleanup.

## 4. Server-side API contract

Recommended endpoint: `POST /api/tts`

Example request:

```json
{
  "text": "Welcome to Anantya 2026.",
  "mode": "page",
  "voiceProfile": "anantya-assistant",
  "format": "mp3"
}
```

Success option A: return audio bytes with `Content-Type: audio/mpeg`.

Success option B: return a short-lived URL to generated audio from approved storage.

Example failure:

```json
{
  "error": {
    "code": "TTS_BUSY",
    "message": "Voice is temporarily busy."
  }
}
```

The client should fall back to browser speech on expected provider/queue failures. It should not expose provider keys or internal error traces to users.

### Server requirements
- [x] Validate the request body and accepted modes.
- [x] Set an application maximum text length.
- [x] Check cache before calling the provider.
- [x] Coalesce identical in-flight requests.
- [x] Apply a bounded concurrency limit and bounded queue.
- [x] Set provider and queue timeouts.
- [x] Apply abuse protection/rate limits.
- [x] Handle provider 429, quota, timeout, auth and 5xx errors distinctly.
- [x] Cache successful audio using a key that includes normalized text, provider/model, voice ID, output format and settings/version.
- [x] Do not cache personalized/private chatbot responses in a shared cache.
- [x] Keep the API key on the server only.
- [x] Add structured logs without secrets or unnecessary full text.

If the existing workspace does not contain a suitable backend, implement the client against a mock API for local development and document the required server integration. Do not call ElevenLabs directly from browser code with a secret key.

## 6. Readable page content contract

Preferred host integration:

```javascript
const readableContent = getCurrentPageReadableContent();

await tts.readPage(readableContent);
```

The host website can provide structured text directly, which is more reliable than scraping the entire DOM. If a selector is needed, make it configurable and document it.

Extractor requirements:
- [ ] Read visible text only from the chosen content root.
- [ ] Exclude `script`, `style`, `noscript`, buttons, form controls and explicitly excluded regions.
- [ ] Exclude hidden elements and repeated navigation/footer content.
- [ ] Preserve headings and logical order.
- [ ] Normalize whitespace without removing meaningful punctuation.
- [ ] Split content at paragraph/section boundaries before splitting long paragraphs.
- [ ] Avoid generating audio for an empty result.

DOM visibility checks can differ across frameworks and browser layouts; add tests using representative page fixtures.

## 7. Playback and fallback state machine

Suggested states:

```text
idle
  -> loading
  -> playing
  -> paused
  -> playing
  -> idle

loading / playing
  -> fallback
  -> playing
  -> idle

loading / playing / paused
  -> stopped
  -> idle

any active state
  -> error
  -> idle
```

Requirements:
- [x] One active speech session per browser tab by default.
- [x] Starting chatbot speech stops page reading, and vice versa.
- [x] Stop cancels current playback and any client-side pending request.
- [x] Ignore late responses belonging to an obsolete request/session.
- [x] Reset UI state in success, error, stop and cancellation paths.
- [x] Browser fallback uses `window.speechSynthesis` only after checking support.
- [x] Stop existing browser utterances before starting another to prevent overlap.

## 8. Tests

### Unit tests
- [x] Chatbot answer is spoken only when voice is enabled.
- [x] TTS receives the final answer, not the user's question.
- [x] Page text extraction excludes navigation and controls.
- [x] Empty and oversized input are handled.
- [x] Cache key changes when text/voice/model/settings change.
- [x] Duplicate concurrent requests are coalesced.
- [x] Concurrency and queue limits are enforced.
- [x] 429, timeout, quota and 5xx failures trigger fallback.
- [x] Stop/cancel prevents stale audio from playing.
- [x] Playback state is reset after errors.
- [x] Missing Web Speech API is handled without breaking the chatbot.

### Integration/load tests
- [ ] Multiple simultaneous users requesting the same page chunk cause one generation where the cache/coalescing layer is shared.
- [ ] Different uncached requests respect the configured concurrency and queue limit.
- [ ] Queue overflow returns a controlled error and activates browser fallback.
- [ ] Provider outage and exhausted quota do not break page navigation or chatbot text.
- [ ] Verify that client bundles and browser network requests do not reveal the ElevenLabs key.
- [ ] Test in the actual supported browsers and mobile devices.

## 10. Definition of done

- Both modes work independently.
- The same TTS manager handles playback and cancellation.
- ElevenLabs credentials remain server-side.
- Page audio and safe reusable audio can be cached.
- Queue and concurrency limits are bounded and configurable.
- Browser speech fallback works when the provider fails.
- Tests cover the critical success and failure paths.
- Setup instructions and integration contracts are documented.
- Existing chatbot behavior and unrelated website functionality remain unchanged.
